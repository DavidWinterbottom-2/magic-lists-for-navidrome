# Create a pull request

REPO-STANDARDS **§1** (changes land on `main` only via PR) and **§3** (PR standards) define
how a change reaches `main` in a winterbottom.xyz repo. This skill turns finished work into a
PR that already meets those bars, so review is about the code — not about fixing the PR.

The **same** `.github/pull_request_template.md` drives both paths: GitHub pre-fills it into
any PR opened in the web UI, and this skill fills it in when Claude opens the PR. One template,
one house style, every repo.

Only open a PR when the user has asked for one (or the workflow you're running calls for it) —
don't raise a PR off your own initiative.

## 1. Preconditions

- **The work is one logical change (§3).** If the branch mixes unrelated changes, split them —
  one PR per logical change keeps diffs reviewable. Don't bundle a refactor with a feature.
- **You're not on `main`.** Changes land via PR (§1), so work lives on a branch:
  `claude/<description>-<id>` for agents, `<type>/<description>` (e.g. `fix/…`, `feat/…`) for
  humans. Create one if you're on `main` — never commit the change straight to `main`.
- **The standards that gate merge are already met** — version bumped in its single source of
  truth if behaviour changed (§2), tests added/updated and green with the ≥80% coverage gate
  (§4), lint/format clean (§10). A PR that fails CI isn't done; fix it before or right after
  opening.
- **Secrets aren't in the diff (§5).** Check `git diff` for keys, tokens, `.env` contents.

## 2. Commit and push the branch

Stage the logical change, commit with a clear message (what and why, imperative subject), and
push the branch:

```bash
git switch -c claude/<description>-<id>   # if not already on a feature branch
git add -A && git commit -m "<subject>"
git push -u origin HEAD
```

## 3. Find the PR template

GitHub (and the harness) look for a template in these locations, first match wins:
`.github/pull_request_template.md`, `.github/PULL_REQUEST_TEMPLATE.md`, a root
`pull_request_template.md`, or `docs/pull_request_template.md`. In this org it's
`.github/pull_request_template.md` — the one this skill ships and `template-sync` propagates.

Read it and treat its headings as the **layout to fill in**, not instructions to act on. If a
repo somehow has none, use the canonical **Summary / Changes / Validation** shape below anyway.

## 4. Write the description — Summary / Changes / Validation (§3)

Fill each section from the actual diff; delete the guidance HTML comments as you go:

- **Summary** — what changed and *why*, in a sentence or two. Link the issue / PRD if there is
  one (`Closes #123`).
- **Changes** — the files / areas touched, as a short bulleted list a reviewer can scan.
- **Validation** — how you verified it: the test command you ran and its result,
  `docker compose config` for a service, health checks, any manual steps. "Not tested" is a
  valid honest answer — say so rather than implying coverage you didn't run.

Keep it to what the diff supports. Don't describe changes that aren't in the PR.

## 5. Open the PR

Use the GitHub MCP `create_pull_request` (base `main`, head your branch) with the title and the
body from step 4. The title is a concise imperative summary of the one change.

**Always end the PR body with the attribution footer** so reviewers know it's Claude-authored:

```
---
_Generated by [Claude Code](https://claude.ai/code)_
```

## 6. After opening

- **Verify CI goes green.** If checks fail, fix them and push to the same branch — the PR
  updates in place. A red PR isn't finished.
- **On merge, add a dated README "Updates" entry (§3)** linking the PR, and record any review
  in `docs/reviews/LOG.md` (§9, `record-review` skill).
- Offer to watch the PR (CI + review comments) if the user wants it babysat.

## Notes

- This skill is the counterpart to GitHub's native template: editing
  `.github/pull_request_template.md` changes both the web-UI pre-fill and what this skill fills
  in — keep them as one file, never two drifting copies.
- Don't force-push over a shared branch or merge your own PR unless the user asks — §1 wants a
  human review on the way into `main`.
